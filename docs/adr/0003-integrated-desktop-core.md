# ADR-0003：独立应用窗口与内置协议核心

状态：Accepted，2026-10-17；实现进度与尚未通过的验收项见 [内置重构进度](../integration-progress.md)。

## 背景

v0.3.1 的 Windows EXE 启动 HTTP 网关后调用默认浏览器；部分来源仍需下载上游程序、安装 Node/Python 或运行外部客户端。它统一了操作入口，没有达到用户要求的核心融合和完整交付。

用户明确要求 EXE 自身提供应用窗口，内置各来源的协议、反代及相关算法，不让用户另行下载上游。“融合”不能仅指打包几个现成 EXE 或隐藏版本选择。

## 决策

1. Windows 使用应用自己的窗口，延续简约、大字号界面及独立后台入口。保留共享 HTML 是可选实现方式；若采用嵌入式渲染器，必须解决干净 Windows 的离线运行依赖，不能要求首次启动联网补装。框架选择待实测确定。
2. 将来源的协议转换、流式处理及反代能力作为应用核心模块开发。共用凭证隔离、模型目录、取消和背压等基础设施；不以下载并拉起上游程序作为完成集成的标准。
3. 第三方代码复用须记录来源、固定提交、许可证和修改范围。重新实现或复用经过审查的代码均可，取消 ADR-0001 和原 AGENTS 规则对上游代码导入的笼统禁止。保持模块小而可审计，不整仓搬运。
4. 必不可少的浏览器等运行资源在构建、安装包交付时包含；应用正常启动和来源准备不得再运行 winget、npm、pip 或下载上游发布包。模型请求和本人账号授权仍需相应网络与权限。
5. 六个来源保持可选、默认关闭。无头V和本地同源实现合并为同一能力，不增加第七个来源或让用户选择运行版本。保留快速V必填 Express API Key、单一客户端 URL、逐步引导及后台用途说明。
6. 保留模型命名空间、明确目标的别名、独立管理认证与禁止静默跨来源回退。内置不改变服务方的认证要求，不替用户登录或确认规则。

## 边界与交付

此决策取代 ADR-0001 的外部组件交付方案及 ADR-0002 的受管组件/外部浏览器方案，其余安全和路由规则继续适用。旧版本文档保留为历史事实。

本地 modified 无头V EXE 不能用来声称源码已集成；其精确源码尚不可复现，应从可核验来源梳理能力并记录差异。WorkBuddy 的客户端依赖、Codex 的授权/会话能力、AI Studio 的浏览器依赖需要逐项验证；未替代的依赖必须明确记录，不能将仍需用户额外安装的来源标为完成。

本轮目标是 Windows 一体化。Android 继续纯 Java，保持共享配置与管理页面；每项能力的实现/桥接/未支持状态单独说明，不能把桌面重构宣传成 Android 也已全部内置。

具体通过条件见 [一体化桌面应用规格](../spec-integrated-desktop.md)。实现完成前，不以新 Release 宣称已满足该架构。
